# Required amendments to the directive

## Separate identities and ownership

A HubSpot deal is the opportunity. A client is its associated company. A SOW is a separate governed package. Preserve all three and their relationships. Distinguish company account owner, deal sales owner, local action assignee and delivery owner. A company can have deals owned by several people; do not select an arbitrary deal owner as its account owner.

Resolve hubspot_owner_id against HubSpot owner id, not HubSpot userId or a DealGate user UUID. Include archived owners for historical display. A missing local login does not mean missing CRM ownership. Show Owner details unavailable for an unresolved source reference; reserve Unassigned for an actually empty source owner.

## Replace blanket deletion with a reversible migration

Do not delete every record without a SOW file. First identify the auto-creation path in code and classify candidate records. Preserve any real scope, GM draft, actions, comments, approvals, documents, signed work or project links. Export a dependency manifest and backup; migrate useful data to the correct deal; archive only proven empty machine-created stubs. Record counts and prove rollback. Existing deep links must resolve to the correct replacement record.

## Correct the identifier test

The screenshot contains an 11-digit deal ID, a 10-digit stage ID, an 8-character hash and a UUID. A UUID/12-digit pattern does not catch them all. Assert exact expected names in identity fields, breadcrumbs, tabs, cards, search results and exports. Add targeted checks that known IDs never become display labels. Do not reject legitimate numeric company names, amounts or dates.

## Define deletion by state and authority

A file existing is not enough to permit Delete SOW. Permit authorized draft removal only under the defined recovery policy; preserve approved/executed versions and decision history. Prefer archive or supersede for governed records. Also remove routine Delete client from mirrored client pages unless its local/source behavior, dependencies, authorization and recovery are explicitly defined.

## Close the dependency gap

S19-1b calls next actions and comments slice 2 features, while requiring them on the deal page. The architecture says the next_action model already exists: reuse it and complete its API/UI rather than creating a competing model. Include working comments or name their dependency and mark the journey incomplete. Do not substitute placeholders or zero counters. Read the exact S15/S17 files and resolve both test-gate commands from the repository before coding.

## Preserve the latest agreement display rule

The supplied S17 rule asks for client-level documents-on-file indicators. Keep separate NDA and MSA checkmarks with file links, uploader/time and an explicit On file meaning. Do not label upload alone Signed or Legally approved. Earlier documents contain stronger coverage controls; reconcile that difference explicitly. This repair must not silently introduce new legal blocking rules or remove existing SOW Legal review.

## State changes must be enforced on the server

Every advance checks identity, permissions, required evidence and current versions. A disabled button is insufficient. A price, scope, staffing-cost or other material change creates a revision and invalidates affected approvals. A second browser tab cannot approve an obsolete package. Retrying a decision, upload, signature request or handoff cannot duplicate side effects.

One deal can have multiple SOWs. Each SOW needs its own gate, value, version and approval history; an aggregate label must not claim all are approved because one is. Signed value, open deal value and recognized revenue are separate measures.

Internal review signoff, client execution and delivery acceptance are three distinct events. The end-to-end test must exercise all three, including a rejected or returned package and its successful resubmission.

# Data boundaries migration and operational controls

## One query layer and explicit ownership

The CRM mirror holds companies, deals, company-deal associations, owners, pipeline/stage metadata, configured custom-property metadata and activity references. HubSpot owns these commercial facts. Local records hold agreements, SOW/document versions, GM versions, review packages, decisions, conditions, actions, comments, groups, projects, forecasts, actuals, renewals and audit events. Preserve the architecture attachment\'s current read-only HubSpot boundary; the three governance writeback properties remain a separate future story.

Reuse working models and services after inspecting the repository. Do not introduce a second opportunity model or an independent source of truth for the same field. Extend the existing query service to join the local workflow records. Identify source, freshness and completeness in the response so every screen uses the same meaning.

## Synchronization must preserve business history

Use supported events plus reconciliation; hydrate the current source record and handle out-of-order/duplicate delivery safely. Synchronize owners, stage definitions, Business Unit option labels and associations as well as deals. Handle property clears, merged/deleted CRM records, archived owners and pipeline changes. Preserve contracts and history when CRM records disappear. Surface failed or partial syncs with their business impact.

Custom-property configuration needs type-aware extraction, option-label resolution, filtering and rendering. A new field is only a one-line change when its type is already supported. Report the discovered Business Unit mapping and evidence. Determine note-sync capability and permissions for the actual integration rather than assuming an API scope or webhook event.

## Migration sequence

1\. Inventory models, routes, data sources and S15/S17/S19 directives; record existing behavior and the exact test gates. 2. Produce read-only counts and a source-to-screen comparison. 3. Back up candidate stub records and dependencies. 4. Stop proven unwanted auto-creation. 5. Migrate legitimate local content, archive only proven empty stubs and redirect legacy routes. 6. Reconcile counts, attachments, decisions and links; verify rollback. Do not delete a CRM deal to remove a UI stub.

## Access and recoverability

Apply the same permissions to API reads/writes, aggregates, search, groups, exports and document downloads. CRM ownership does not grant a local approval role. Staff cost detail remains restricted. Preserve the actor, before/after state, package version, reason and timestamp for governed changes.

Actions fail visibly with a safe retry. A retry must reconcile a possibly successful first attempt rather than repeat it blindly. Imports detect duplicates and show partial reconciliation. Notifications track attempted, delivered and failed states; use production recipients only when authorized. Tests use controlled destinations and staging records.

## Honest status language

Use Unknown, Not assessed, Not configured, Processing, Failed and Stale where appropriate. Reserve zero, none, approved and complete for verified states. In particular, unavailable GM cannot yield No blockers; a missing action model cannot prove zero overdue actions.

# Additional findings from the architecture rundown

These are contradictions or risks in the supplied architecture description. They identify specific code checks; they are not claims that the corresponding runtime defects have been reproduced.

## A1 Ownership and SOW relationships need explicit correction

The diagram exposes opportunity.owner_id pointing to a local user, while the desired owner is a HubSpot identity. Add or verify a separate source owner reference and resolve it through the owner mirror. An optional local-user mapping serves tasks and access only. The described one-SOW-per-opportunity relationship also conflicts with S19-1b\'s list of SOWs. Inspect foreign keys and uniqueness constraints before changing the UI; support independent SOW packages without duplicating the CRM deal.

The upload flow describes multipart file plus client picker, but does not show deal binding. Carry and validate both client and deal through upload, extraction, confirmation and package creation. It also describes governance_status on the opportunity and clearing a release flag after release. Keep authoritative gate/release state per SOW; define an explicit deal rollup so one released SOW cannot conceal another pending package.

## A2 A five minute schedule cannot guarantee two minute freshness

The architecture promises at most two minutes from event to UI, while the consumer starts every five minutes. An event arriving just after a short-lived worker exits can wait nearly five minutes, plus startup and processing. Either run a continuously available consumer or publish an honest measured target. Verify that MaxNumberOfMessages 10 is a batch within a draining loop, not a limit of ten per scheduled run. Add backlog age, DLQ and processing-lag alerts; manage overlap and visibility extension.

A successful worker tick is not proof the dataset is current. Separate heartbeat, last successful source fetch, processed event watermark, oldest queued event and last completed reconciliation. Render the correct source-specific freshness; a successful unrelated worker must not reset the Pipeline synced banner.

## A3 Resume and archival must share a completed scan generation

The described backfill marks not-seen deals archived and resumes from a saved cursor after failure. Archive only after an authoritative full scan completes. Persist the scan generation and seen-set across resumes, distinguish filtered scans, and prevent overlapping generations from archiving one another\'s records. A failure after one page must archive nothing. Use conservative deletion confirmation where the source listing is not a stable snapshot, and preserve contracts on source deletion.

## A4 Transport identity is insufficient for business deduplication

The narrative mentions SQS message ID; the standing rules require source event ID. Retries of one HubSpot event can arrive as different queue messages. Use a verified stable source event key or documented composite with a database uniqueness guard. Commit record changes, audit and notification outbox atomically before acknowledging the queue message. Idempotent row upserts alone do not prevent duplicate audit entries, tasks or notices.

## A5 A single service and three SQL calls do not prove correct totals

The architecture derives attention flags and SOW state in Python after fetching rows. That is acceptable for display, but filtering and pagination must apply their equivalent predicates to the full authorized set before limiting rows. Otherwise page lengths, totals and groups can disagree. Likewise, stage buckets grouped only by label can merge different pipelines. Use pipeline/stage identity in aggregation and labels for display. Measure rows scanned and latency; a SQL-call count is not a substitute for query plans or correctness tests.

## A6 Release delivery must include workers and compatible UI

The supplied deployment updates the API task definition and publishes the web build in parallel, while seven scheduled task definitions share the image. Verify that every relevant worker receives the tested immutable image version and environment configuration. Publishing a new UI before a compatible API/migration is ready can break an otherwise valid build. Use backward-compatible schema/API changes and controlled promotion, record each component version and prove rollback.

The described workflow triggers on main, but the directive requires staging and product-owner click-through before merge. Show the actual branch-to-staging deployment path and protected promotion gate. Do not assume main-only deployment satisfies that requirement. Preserve Terraform-only infrastructure changes and the existing CI carve-out.

## A7 Extraction and immutability require precise lifecycle boundaries

The upload narrative says queue extraction but also says extraction is synchronous. Inspect the actual path and make progress, timeout, cancellation and retry behavior match it. For lengthy work, persist job state and provide polling/status recovery. A schema-valid AI result is still a draft requiring human confirmation. Preserve immutable SOW/GM/decision evidence; keep mutable workflow status in a clearly identified projection or event-driven state record rather than modifying approved versions.

## A8 Production claims must reflect current infrastructure

The rundown lists dev-only HTTP origin traffic, single-AZ database, WAF deferred and SES sandbox, while the top diagram includes WAF. Mark these consistently as current or planned. SES sandbox constrains recipients and must not be shown as general production notification readiness. These are production-readiness checks, not a reason to delay independent UI repairs.

Verify /api caching is disabled or safely private and Authorization is forwarded, SPA rewriting excludes APIs, and webhook signature checks use the correct external URL, method, timestamp and body. Verify Cognito issuer, signature, expiry, intended client and token_use, then server-side role/scope checks. ID-token use alone is not proof of a vulnerability; its validation and authorization contract must be explicit. Confirm scheduled test-data cleanup cannot touch untagged client records.
