3. SPA deep-link /sows/xyz:
   GET /sows/xyz
   → text/html
   → cache-control: no-cache, no-store, must-revalidate
   → x-cache: Miss from cloudfront
   → body: <!doctype html>…<title>DealGate</title>…

Previously `/api/nonexistent` returned the SPA index.html at 200

behaviour (S3 origin), not on `/api` or `/api/*` behaviours —
so API errors now round-trip verbatim.

## Design notes (things reviewers should know)

### The scheduler workers are poll loops, not one-shot

`worker.alert_scheduler`, `worker.notification_sender`, and
`worker.renewals_scheduler` all have a `POLL_INTERVAL_SECONDS`
env-tunable poll loop. EventBridge invokes `RunTask` on the
schedule, which launches a new Fargate task that then runs
its poll loop forever until stopped.

That's a **design mismatch**: with a 5-minute EventBridge cadence
and a 60s worker poll, every RunTask launches a task that keeps
polling until something kills it. Left unchecked, the number of
concurrent tasks grows without bound. `worker.audit_export` is
one-shot (correct pattern for EventBridge invocation).

The proof session ran the schedulers as one-off `run-task` calls
and stopped them manually. In steady state the EventBridge trigger
also launches tasks — so tomorrow morning the cluster is going to
have alert_scheduler, notification_sender, renewals_scheduler each
holding open a Fargate task 24/7 unless the ECS scheduler's default
task-timeout kills them (Fargate has no idle timeout — tasks run
until they exit).

**Follow-up ticket needed**: refactor these three workers to run
one tick then exit, matching the audit_export pattern. Scope:
delete the `while True: await asyncio.sleep(POLL_INTERVAL_SECONDS)`
loop, keep the tick body, exit 0. Small change, safe. Not blocking
because Fargate cost per task is minimal ($0.04/hr for 256 CPU /
512 MB) and the tasks do real work each tick — just wasteful.

### CloudFront config: don't merge s14a.1b's changes without re-reading this apply

Apply G added `aws_cloudfront_function.spa_rewrite` + the new
`custom_error_response` set to the CF distribution. When
s14a.1b lands the sows bucket migration + the wider drift
imports, `terraform plan` will still show CF as unchanged
because the state is now correct. But if a rebase drops the
spa_rewrite change back out of module.web, the S14a bug reappears
and the curl proof breaks. Any code review of s14a.1b's web
module diff should confirm spa_rewrite is preserved.

### The scheduler → auth graph decoupling should stay

`module "schedulers" { cognito_user_pool_id = "" cognito_client_id = "" }`
is deliberate. Setting either to `module.auth.*` chains
`schedulers → auth → cloudfront_distribution` on every plan and
was the root of the "one apply became four" problem. The
scheduler workers don't use these vars — they're env decoration.
See the long-form comment in `infra-tf/main.tf` for the reason
(so nobody undoes it thinking they're cleaning up).

### SES sandbox: recipients

Only `srikanthp+dealgate-staging@smartek21.com` is verified. Any
notification whose recipient isn't in the verified list will
error with `MessageRejected: Email address is not verified`.
Options for the future: (a) verify each recipient one-by-one
via `aws sesv2 create-email-identity`; (b) request SES
production access. The `docs/directives/s14a.3-schedulers.md`
directive plans (b) for prod.
