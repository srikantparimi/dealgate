## HAR diff — what actually broke the first attempt

`docs/reports/s12/upload-requests.log` (captured this session):

```
→ POST https://d1mu2un4hj9akj.cloudfront.net/api/sows/upload
  headers.content-type=multipart/form-data; boundary=...
  headers.authorization=Bearer eyJraWQiOiJH... (id token, cognito:groups includes officeapp-e2e)
← 200 POST https://d1mu2un4hj9akj.cloudfront.net/api/sows/upload
  content-type=application/json
```

CloudFront delivered the multipart POST unchanged. The API returned
JSON. My earlier "CloudFront drops multipart bodies" hypothesis was
wrong — noted in the S12 correction message.

The **actual** first-round blocker was the URL the frontend navigates
to on `done`: `SowStudio.tsx:80` calls `nav("/sows/${oppId}/staffing")`,
not `/sows/new?opportunityId=<id>`. My spec's `page.waitForURL(/opportunityId=/)`
matched neither shape and timed out. The fix was to accept either URL
and extract the opportunity id from `/sows/<uuid>/staffing`. Second
fix was to explicitly `page.goto('/sows/new?opportunityId=<id>')`
after the pipeline resolves, so step 1's screenshot is the confirm
screen and not the staffing page.

The API-context call from the previous attempt returned the SPA HTML
because CloudFront's distribution-level `custom_error_response` rewrite
maps ALL 4xx → `/index.html?200`, and that path swallows real API
errors too. Filed as `docs/backlog/s13-cloudfront-api-error-passthrough.md`.
