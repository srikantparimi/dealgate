## Surprises

The surprises, in order of weight. First, on the SQLite test engine a per-deal savepoint committed its page early, so a page that later rolled back still kept its first deal; PostgreSQL (staging) nests savepoints correctly, and an opt-in explicit-BEGIN test engine (I2) now makes the page-atomicity tests behave the same way. Second, before this change one HubSpot deal deleted past the recycle bin (archived lookup 404) would have failed the archive pass, and so the whole nightly scan, every night; it is now listed and left alone. Third, preparing item 7 found that turning webhooks on would still lose events silently: neither the API nor the workers hold KMS permission on the encrypted HubSpot queue, and the router returns 200 when the enqueue fails. Fourth, the existing SystemAdmin trigger always hits CloudFront's 30-second limit on staging (HTTP 504) while the run completes on the server, so its result must be read from sync-health, not from the response. Finally, new deals reach DealGate with no 'Confirm engagement type' intake task, because only the (disabled) webhook path creates it; the first sync after the deploy updated 74 deals, all genuine HubSpot changes (2 closed won, 2 closed lost today), and reopened none.
