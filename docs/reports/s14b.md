## What's in the merged tree

**Header CTA is a single state machine merged with S15/D6.**
`web/src/pages/v2/SowWorkspace.tsx:224-239` renders exactly one primary
action per state, dispatching on `step.action` / `step.href` /
`step.label` returned by
`web/src/pages/v2/sow-workspace/readiness.ts::nextStep`. S14b extended
the existing S15/D6 `WorkspaceSnapshot` interface with `approvalHistory`
and the `NextStep.action` field rather than shipping a second machine —
verified during conflict resolution and again in the compliance review.
"Complete scope" then showing nothing is fixed:
`sow_confirmation.py` now atomically stamps `SowVersion.confirmed_at`
and `confirmed_by`, and the readiness panel says
`"NDA missing — blocks signature, not review"` (`readiness.ts:100/107`).

**Five approval groups.** `api/app/services/approval_routing.py:18-22`
enumerates `delivery`, `hr`, `finance`, `legal`, `executive`. Executive
membership is CEO-derived (Cognito `CEO` group + time-bound delegation)
and cannot be saved via `PUT /approvals/groups/executive`; the endpoint
422s so the ceremony stays with the CEO identity. Settings screen:
`web/src/pages/v2/settings/ApprovalGroups.tsx`.

**Submit flow.** `web/src/pages/v2/sow-workspace/SubmitApprovalDialog.tsx`
opens on the header CTA and calls `POST /approvals/packages/{opp}` with
the frozen SOW version + GM version and the four function assignments
pre-filled from group defaults. Server-side, `submission_plan` +
`submit_package` (`services/approvals.py`) validate group membership,
filter the submitter out, and create `ApprovalAssignment` rows with SLA
due dates.

**Pending-with stream + 20 s poll.**
`web/src/pages/v2/sow-workspace/ReviewStream.tsx` renders per-function
`ApprovalAssignment` rows (assigned name + due date + aging + package
versions), the CEO exception card when the floor gate escalates, and
decisions. Live update lives on the parent —
`SowWorkspace.tsx:103` calls `refresh()` every 20 s while the Approvals
tab is active; the `Updated Ns ago` badge reads the delta.

**No NDA/MSA approval routing.** `check_msa_and_nda_executed` is called
only at signature time (`signed_sow.py:72`, `approval_workflow.py:240`),
never at review — matches both the s16a directive and the S14b readiness
panel copy.

**Header hygiene.** Owner UUID → `OwnerRef` (`RecordHeader.tsx`),
breadcrumb → client → SOW title (`WorkspaceHeader.tsx`), SOW title →
extracted `sow_title` (or `title`) with the hash relegated to the meta
line, Type/Delivery values or the field is omitted (see
`workspaceTitle` in `readiness.ts:327`).

## Two-user approval proof (staging)

`tests/e2e/specs/23-s14b-two-user-approval.spec.ts` drives the full
flow against `https://app.dealgateapp.com` in two Cognito browser
contexts:

1. Owner browser (e2e-staging) uploads the Peppermill fixture (with a
   64-byte random suffix so `file_hash` dedup doesn't short-circuit),
   picks a new client tagged `S14b e2e <ts>`, and calls
   `POST /dev/seed-approved-package/{opp}` to drive scope confirmation +
   minimal GM + a `pending_delivery_hr` package. The seed was extended
   to also insert `ApprovalAssignment` rows using each group's default
   approver (`api/app/routers/dev_seed.py`) so the ReviewStream renders
   per-function Approve controls — commit `8b9593b`.
2. Approver browser (`srikanthp+approver-delivery`) opens
   `/sows/{opp}/approvals`, fills the Delivery reason textarea
   (`"Reviewed scope, staffing plan and GM. Numbers match the SOW."`),
   clicks the Delivery `Approve` button. Server-side `authorize_decision`
   + `decide` accept the call because `AuthUser.id == assignment.approver_id`
   (both are the Cognito sub after re-materialising the user, see
   Follow-ups) and the actor is a Delivery group member.
3. Owner browser refreshes the approvals tab; the 20 s poll picks up
   the update and shows the Delivery `Approved` card with the approver's
   reason within one cycle.

## Follow-ups (documented, not blocking)

- **Cognito → DealGate user id parity.** Admin-invited users get a
  random UUID as `user.id`, but Cognito sign-in produces `AuthUser.id`
  from the `sub` claim. `can_decide` in `approval_workflow.py` compares
  `actor_id == assignment.approver_id`; when the assignment was created
  from a group whose default was an admin-invited row, the comparison
  fails. This slice sidestepped it by deleting the two seeded rows and
  re-materialising them via `POST /sows/upload` (so ensure_user creates
  them with the Cognito sub as id), then re-saving the Delivery group.
  Longer term either the admin invite should accept an explicit id, or
  `ensure_user` should reconcile the row id when adopting by email
  (with all FK sweeps).
- **`hydrate_from_cognito` needs `cognito-idp:AdminGetUser`** on the
  task role. Currently the freshly-materialised approver rows read as
  `Name unavailable` in the ReviewStream — the identity is correct, the
  display is not. See s16a follow-ups.
- **SES verification of `srikanthp+approver-delivery` and
  `srikanthp+ceo`** is Pending as of report time — the account is in
  sandbox mode, so outbound approval-notification emails to those
  addresses will bounce until Kanna clicks the verification links. The
  in-app flow (owner + approver both logged in via Cognito) does not
  depend on this.
- **`ALLOW_DEV_SEED_ENDPOINT`** re-attached by hand; adopt into TF.
  Same follow-up as s16a.
