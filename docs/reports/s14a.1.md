## Import batch 1 — sows bucket — STOP + quarantine

**Command:** `terraform import 'module.storage.aws_s3_bucket.sows'
officeapp-dev-sows-669810405473` — succeeded (import into state).

**Immediate follow-up plan** (`terraform plan -target=…`):

```text
# module.storage.aws_s3_bucket.sows must be replaced
-/+ resource "aws_s3_bucket" "sows" {
    ~ object_lock_enabled = false -> true  # forces replacement
    ...
Plan: 1 to add, 0 to change, 1 to destroy.
```

The existing bucket was created (probably by console/CLI months ago)
**without S3 object lock**. The Terraform code
(`infra-tf/modules/storage/main.tf`) requires object lock ENABLED —
part of the S7 audit-hardening story ("SOW uploads are tamper-proof
via S3 object lock; retention 7 years"). Object lock is a
bucket-creation-only flag; changing it forces bucket replacement,
which destroys every SOW currently in the bucket.

**Reverted the import** via `terraform state rm
'module.storage.aws_s3_bucket.sows'`. State is back to its pre-import
snapshot; no AWS change was made.

**Disposition options (Kanna to decide):**
- **A. Adopt as-is, weaken the code.** Change
  `object_lock_enabled = true` → `false` in the storage module. This
  gives up the S7 audit-hardening promise for the sows bucket. Would
  need a follow-up story to relocate SOWs into a new object-lock
  bucket via a controlled migration + backfill.
- **B. Create a new object-lock bucket, migrate + retire the old.**
  Terraform declares `officeapp-dev-sows-v2-…` with object lock on;
  a data-migration story copies existing keys; API config flip;
  original bucket eventually deleted. Multi-slice work.
- **C. Enable object lock retroactively.** Not supported by S3; the
  flag is set at bucket creation. Would need B.
- Recommendation: **B**. The audit-hardening promise is a
  security-story commitment; adopting a non-object-lock bucket erodes
  it silently.
