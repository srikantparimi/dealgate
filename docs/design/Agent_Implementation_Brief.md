# Implement DealGate V2

Implement the revised interface from `DealGate_UI_UX_Specification.md`, `DealGate_Design_Tokens.json` and `Requirement_Coverage.md`. Use the V2 concept shown in the conversation as the visual and interaction reference. It supersedes the earlier generic dashboard concept.

The first delivery hid too much of the core process in documentation. The following must be visible working screens:

1. Pipeline clients with separate NDA and MSA lifecycle statuses, actual legal entities, owners, next actions, signature evidence and blockers.
2. A six-stage SOW approval board: Draft intake, Scope & GM, Functional review, CEO exception, Client signature, Handoff.
3. A guided New SOW studio with engagement templates, verified extraction, staffing/cost inputs, separate US/India allocation, review routing and submission.
4. A SOW workspace with named Delivery, HR, Finance and Legal decisions, deadlines, evidence and exact version identity.
5. Additional CEO approval below margin, with the project explanation, financial shortfall, alternatives, rationale and structured conditions.
6. Signature gating and signed-SOW distribution with verified recipients, delivery receipts, acknowledgements, billing/staffing setup and release evidence.
7. Renewal review two calendar months before expiry, substantive weekly updates, earlier notice deadlines, short-engagement handling and verified outcomes.

Preserve every other requirement in R01–R28, including AI indicative research, reporting, actuals, access, policy/rates, imports, audit and integration recovery. Do not count a description, a placeholder panel or an unconditional success toast as implemented behavior.

Inspect the repository before coding. Preserve working authentication, services and supported framework. Use a custom token-driven React/TypeScript interface where compatible, with accessible component primitives. Match the distinct compositions: executive banner/readiness matrix, lifecycle board, intake studio, evidence/decision workspace and renewal timeline. Merely replacing colors on the old dashboard is insufficient.

Use the implementation sequence in the specification. If parallel agents are authorized and available, divide ownership across shared visual components, client/agreements, SOW/GM, approvals/handoff, delivery/renewals, reporting/AI and integration/testing. Coordinate shared contracts and integrate continuously. No arbitrary deadline justifies removing a requirement.

Continue independent work when an external dependency is blocked. Record the blocker, affected requirement, safe development adapter and production configuration needed. Never bypass a business control, permission, approval or failed test to declare completion. An offline connector must remain visibly unavailable.

Keep US35% and India50% rules; test each applicable geography independently with decimal arithmetic and full precision. Bind all reviews to exact SOW/GM/policy versions. Material changes create fresh review. Do not let a technical administrator become CEO, a CRM win become release, a file upload become legal execution, or an AI estimate become an authoritative GM.

Test real user journeys through connected screens and server transitions, including rejected/reworked/stale packages, missing agreements/costs, multiple SOWs per client, conditional approval, expired CEO authority, changed signed terms, duplicate events/imports, failed delivery/retries, month-end and short-assessment renewals, and unauthorized search/export/API access.

Finish with a requirement-by-requirement report listing screen, server behavior, integration status and test evidence separately. Include real browser screenshots, accessibility findings, actual configuration, known defects and unresolved blockers. Claim completion only for work actually implemented and verified.
