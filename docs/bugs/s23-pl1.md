## Decisions for Kanna

- **D1 — Run records get a new table.** No existing table records individual runs: `sync_status` holds one row per source and `audit_event` holds page checkpoints. Migration `20261014_0069_sync_run` adds `hubspot_sync_run`: kind (`nightly` / `manual` / `test`), started_at, finished_at, status (`running` while in flight, then `ok` / `partial` / `failed`), deals_seen, deals_written, error_count, errors (max 5 `{hubspot_id, reason}`), fatal_error, counts. Status: done.
- **D2 — What "wrote deals" means.** `deals_written` counts every deal the run saved from HubSpot: created, changed, and unchanged ones it re-confirmed (each bumps `hubspot_last_seen_at`). A quiet night with no changes is still a success. Archived rows are reported in `counts.deals_archived`.
- **D3 — Status rules.** A fatal error gives `failed`. Errors with nothing written also give `failed`, because HubSpot could not be read usefully. Errors with deals written give `partial`. No errors gives `ok`. An `ok` run that wrote nothing (an empty portal) does not move `last_success_at`, because the contract requires that the run "wrote deals".
- **D4 — State precedence.** `failed` when the last attempt ended `failed` or `partial`. Otherwise `fresh` when the last success is within 36 hours (36 h counts as fresh). Otherwise `stale`. The contract's clause "stale ... and no newer attempt exists" is covered: a newer attempt is either failed or partial, giving `failed`, or ok, in which case it is the last success. A run still `running` is ignored for 2 hours. After that it counts as failed with the reason "run did not finish", and the next run closes it.
- **D5 — Before the first run row.** Right after deploy, sync-health falls back to `sync_status.hubspot_backfill.scan_completed_at`. Only `complete_scan` writes that value, when a full deal scan finished, so it is never the heartbeat. With no completed scan at all, the state is `failed` with the reason "no completed deal sync recorded".
- **D6 — An unknown stage is an error, not a guess.** A deal whose stage the map cannot resolve is not written, whether new or existing. It is listed as `deal: stage <id> not mapped`. This revises S19 G11, which stored the raw stage id with open flags, the path by which a closed deal would be reopened. The test was renamed to `test_backfill_lists_an_unknown_stage_and_does_not_guess`.
- **D7 — Item 6: the webhook writer goes through the stage-mapping writer; it is not switched off.** `_upsert_opportunity` now requires a stage map and raises `UnmappedStageError` before any write. `handle_event` loads the stored mirror and refreshes it from HubSpot once if the deal's stage is new. Nothing was enabled: webhooks still get 401, the intake schedule is still disabled, and the continuous service is still off.
- **D8 — The webhook path no longer clears secondary companies.** The writer replaces them only when the caller resolved them, as the nightly path does. The webhook path keeps what is stored.
- **D9 — A stage id in two pipelines fails closed.** Neither copy is mapped, and the id is listed as an error.
- **D10 — Owner-list and business-unit problems are partial, not fatal.** Owners are resolved per deal, and the writer never clears a BU value it did not observe, so the deals can still sync safely. A 401 or 403 anywhere is fatal, because HubSpot cannot be read.
- **D11 — Unconfirmed deletions no longer block the scan.** A deal missing from HubSpot whose deletion HubSpot will not confirm is listed and left unarchived, and the scan still completes. Before this change, one such deal failed the archive pass, and therefore the whole scan, every night.
- **D12 — Test stub default pipeline.** `StubHubSpotClient` now defaults to HubSpot's default sales pipeline, with labels equal to the ids. Tests that never configured pipelines therefore keep a mapped stage. `pipelines=[]` still means an empty portal. The stub is used only by tests.
- **D13 — Exit codes.** `failed` exits 1, so the ECS task shows failed. `partial` exits 0, because deals were written, but logs `hubspot_deal_sync_partial` at error level with the HubSpot ids. Sync-health shows `failed` for a partial run.
- **D14 — The legacy `hubspot_reconcile` row tells the truth.** It records success only for an `ok` nightly run. Partial and failed runs write `last_error` ("partial: N record errors" or "failed: <reason>"). Manual and test runs do not touch it. The old page's amber chip therefore shows "Sync error" after a partial or failed night.
- **D15 — The admin trigger's response changed.** `POST /integrations/hubspot/backfill` now returns the run's real `status` (`ok` / `partial` / `failed`) and `run_id` instead of a constant `"complete"`. No script, spec or web code read the old value.

### 7b. The continuous intake service

- **Where it is.** `infra-tf/modules/schedulers/hubspot_intake_service.tf:19-103` defines the task definition and ECS service (one always-on task), with four alarms in `hubspot_freshness_alarms.tf:61-135`. All are gated by `hubspot_continuous_enabled` (root `infra-tf/variables.tf:69-73`, default false; every S22 plan used the default, `docs/reports/s22/deploy.md:15-16`).
- **The exact change.** No code change is needed. Add one variable to the standard whole-root plan: `-var hubspot_continuous_enabled=true`. Expected `Plan: 6 to add, 0 to change, 0 to destroy`. After that, every image roll becomes 13/15/13 instead of 12/14/12.

### Prerequisites before either is useful or safe

1. **Webhooks get 401.** `HUBSPOT_APP_SECRET` and `HUBSPOT_WEBHOOK_URL` are not on the API task (`infra-tf/modules/api/main.tf:374-417`). Without the URL, the signed address is rebuilt as plain `http://` without `/api`, so it can never match what HubSpot signed. Both need Terraform wiring, plus a secret Kanna creates outside Terraform.
2. **HubSpot app settings** (target URL, subscriptions, signing secret) are not recorded in the repo. They were not touched.
3. **The webhook writer.** Fixed on this branch (item 6). It must merge before either consumer runs.
4. **Database connections.** A re-enabled schedule has no cap on concurrent tasks, which is the setup that exhausted the database. Do a one-shot run first, and add a hard wall-clock exit to `worker/hubspot_intake.py`.
5. **Queue encryption (newly found, from the Terraform config, not checked against live IAM).** Both queues use the shared KMS key. Neither the API task role (`kms:ViaService` limited to s3 and secretsmanager, `infra-tf/modules/api/main.tf:166-185`) nor the schedulers task role (no KMS grant) can use it for SQS. A real event's enqueue would likely fail. The router catches that failure and still returns 200 (`api/app/routers/hubspot.py:129-157`), so the event would be **lost silently**.
6. **Continuous-mode defect.** The worker's error count never resets (`worker/hubspot_intake.py:98-116`). After one failed event, the heartbeat stays unhealthy and the lag alarm stays in ALARM for up to 24 hours. Separately, the alarms notify no one unless `operational_hardening_enabled=true`, and the DLQ runbook they cite does not exist.

### Needed now? No.

The nightly reconcile at `cron(0 4 * * ? *)` (21:00 PDT) keeps deal data within about 24 hours, inside the contract's 36-hour window. A SystemAdmin sync covers urgent cases. Neither intake path would change the freshness label, which now comes only from deal sync runs. There is also nothing to consume while webhooks get 401. If same-day freshness becomes a requirement, the lowest-risk step is a second daily reconcile, reusing the recorded, stage-mapped path. For minute-level freshness, use the continuous service, not the 5-minute schedule, and only after every prerequisite above.

## Item 8 — consumers of the intake heartbeat, changed or left

The intake heartbeat is two `sync_status` rows written by `worker/hubspot_intake.py` whether or not any data arrived: `hubspot_webhook` (once per intake run, `:123-130`) and `hubspot_consumer` (once per poll, `:113-117`). Both have been frozen on staging since 2026-10-01. `hubspot_webhook_received` and `hubspot_webhook_processed` are per-event watermarks, not heartbeats.

**Changed (the heartbeat is no longer a freshness input):**

- `web/src/pages/v2/Pipeline.tsx:194-199` — `summariseSync` takes the label from `GET /hubspot/sync-health` `last_success_at`; the fetch is at `:428` and the call at `:496`. It previously read `hubspot_webhook.last_success_at`. This is the only change in this file.
- `web/src/api/client.ts:4549` — added `getSyncHealth()` and the `SyncHealth` type (additions only, per rule 17).
- `api/app/routers/pipeline.py:402-439` — `_load_freshness` (`meta.freshness` on `/pipeline/opportunities` and `/pipeline/clients`) now takes `state` and `reconciled_at` from the sync runs. The fallbacks to `hubspot_webhook` and the stored-lag rule are gone.
- `api/app/routers/pipeline.py:951-985` — new `GET /hubspot/sync-health`, computed by `api/app/services/hubspot_sync_runs.py:193` from run records only. The fallback before the first run (`:247`) reads the completed-scan time, never the heartbeat.
- `api/app/routers/reports.py:248` — `hubspot_webhook` was removed from the portfolio report's freshness basis (`basis.watermarks`).

**Left (not freshness logic, or outside PL1's scope):**

- `worker/hubspot_intake.py:114, :124` — the producers. Kept as liveness signals: Settings and the T39 e2e spec read the `hubspot_webhook` row, so it must not be deleted.

The directive limits this file to the label. Neither input can hide a stale or failed sync: lag is always 0 after a success, and the chip also reads `meta.freshness.state`, which now comes from the runs. - `infra-tf/modules/schedulers/hubspot_freshness_alarms.tf:105-135` — a log-metric alarm on the consumer heartbeat (liveness, correct use). It exists only when the continuous service is on. No infra edits in PL1.
- `api/tests/test_s20_freshness_injection.py` — five xfail skeletons that assert nothing. Two of them describe freshness driven by queue backlog or the DLQ, which now contradicts the rule. They should be marked obsolete in a follow-up.

## Issues log

- **I1 — Two auth tests fail on main too.** `tests/test_auth.py::test_me_returns_user` and `::test_bearer_jwt_path_used_outside_local` return 503 on an untouched `origin/main` 7ce0b83 worktree, the same as on this branch. They are not caused by PL1. One attempt: reproduced on main. Status: left, pre-existing.
- **I2 — SQLite let per-deal savepoints leak out of a rolled-back page.** pysqlite and aiosqlite emit BEGIN only before the first write. A SAVEPOINT issued first therefore opened the transaction itself, and releasing it committed. `test_nonadjacent_cursor_cycle_...` caught deal "3" surviving its page's rollback. PostgreSQL, which staging runs, nests savepoints correctly. A global fix in the test engine (SQLAlchemy's documented explicit-BEGIN recipe) broke a query-count budget and the export's own SQLite BEGIN. Fix: an opt-in `savepoint_engine` in `api/tests/conftest.py`, used by the three modules that test page atomicity. Status: fixed and tested.
- **I3 — The archive check was unbounded in an outage.** With isolation, an empty live list (HubSpot returning 200 with no deals) would have asked HubSpot about every local deal (672 calls) and outrun the scan lease. Fix: stop after 5 unconfirmed absences, list the rest as not checked, archive nothing unchecked. Test: `test_an_empty_live_list_stops_asking_hubspot_after_five_absences`. Status: fixed and tested.
- **I4 — A lease-refused run masked the real run.** A run started while another holds the scan lease fails at once. Ordering attempts by start time made sync-health report `failed` although the other run finished `ok` a minute later. Fix: the last attempt is the run that ended last. - **I5 — The test suite rewrites a fixture workbook.** `api/tests/forecast/fixtures/forecast_model_synthetic.xlsx` and `..._complete.xlsx` change on every full run. This is pre-existing and not PL1. It was restored before commit. Status: left.
- **I6 — Tests that pinned the old all-or-nothing rules were rewritten to the new ones.** This was needed by items 4 and 5, and every one keeps its safety assertion: nothing is archived without HubSpot's explicit evidence, and closed deals stay closed.

### Found by the adversarial review (four reviewers, each checked by a verifier), all fixed and tested

- **I7 — Failed or partial runs still marked the `hubspot_backfill` row successful.** `complete_scan` recorded success whenever the scan protocol finished. It now takes `error` and keeps the previous success time for a run that refused records ("partial: N record errors" or "failed: …"). The `hubspot_pipeline_mirror` row likewise records "N stage errors". Test: `test_a_partial_or_failed_run_never_marks_the_backfill_row_successful`, `test_stage_errors_mark_the_pipeline_mirror_row`; `test_archived_owner_fetch_failure_is_not_a_successful_complete_scan` asserts it again.
- **I8 — A dead run could hide a later successful run, and closing it re-promoted it.** A run that dies is now ranked at its start time, both while open and once the next run closes it (`finished_at = started_at`). Any run that ended after it supersedes it. Tests: `test_a_dead_run_does_not_hide_a_later_successful_run`, `test_a_closed_dead_run_stays_the_failed_attempt_until_a_newer_run_ends`, `test_a_closed_dead_run_does_not_outrank_a_later_recovery`.
- **I9 — One unavailable secondary company wiped a deal's stored secondary list.** A deal is now refused when any of its companies is unavailable, not only the primary. Test: `test_an_unavailable_secondary_company_blocks_the_deal_and_keeps_its_secondaries`.
- **I10 — Log names claimed success.** A stopped run now logs `hubspot_backfill_stopped` (error), and one with record errors logs `hubspot_backfill_completed_with_errors` (warning). A refused deal logs `hubspot_deal_record_refused`, which no longer collides with the run-level `hubspot_deal_sync_failed`.
- **I11 — Long-standing unconfirmable absences could starve real deletions.** The five-absence outage cap (I3) counted deals that vanished long ago (merged or purged in HubSpot). Those could use the budget every night, so real deletions were never checked. Deals that vanished since the previous scan are now checked first, most recently seen first, and only they count toward the outage cap. There is a hard cap of 25 checks per run. Test: `test_long_standing_unconfirmable_absences_cannot_starve_real_deletions`.
- **I12 — A scan resumed across nights reported fresh on days-old pages.** A failed scan is now resumed only while it started less than 12 hours ago; otherwise it restarts at page 1. Test: `test_a_failed_scan_older_than_twelve_hours_restarts_at_page_one`.
- **I13 — The webhook's stage refresh held stage and audit locks across HubSpot calls, in the reverse order to the nightly.** The refresh now runs and commits in its own short transaction before the event's writes. Test: `test_webhook_stage_refresh_commits_in_its_own_transaction`.
