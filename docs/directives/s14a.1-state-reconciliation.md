# Directive S14a.1: reconcile Terraform state, then unblock S14a apply

From: Kanna Parimi, product owner. 22 September 2026. Commit as
`docs/directives/s14a.1-state-reconciliation.md`. Follow-on to S14a
after step 1 (code-only ship) landed. This slice removes the blocker
that stopped the S14a Terraform apply — 61 resources drifted out of
`terraform.tfstate` from months of hand-applies.

## Why

The `terraform plan` for `infra-tf/` (the currently-live env) shows
55 unrelated creates + 8 unrelated changes on top of the two S14a
items. Applying `terraform apply` would provision observability,
storage, KMS, schedulers, secrets, and IAM resources that were
already created by console/CLI in earlier sprints. Also:
`infra-tf/env/staging/` (the "future staging" root) has never been
applied, errors on a missing ALB data source, and would be a fresh
101-resource bring-up — the layout is dual and confusing.

## Scope

1. **Migrate state to S3 backend with locking.** Uncomment the
   `backend "s3"` block in `infra-tf/backend.tf` (bucket, key, region,
   `dynamodb_table` already listed), create the bucket + lock table
   (via TF or a one-time bootstrap script recorded in the report),
   run `terraform init -migrate-state` to move local state.
   Delete `infra-tf/terraform.tfstate` from any dev laptop after
   migration is confirmed.

2. **Adopt the 61 drifted resources with `terraform import` /
   `import` blocks** (Terraform 1.5+ import blocks are preferred;
   plan-first, apply-empty). Categories to adopt:
   - `aws_acm_certificate.web[0]` — dealgate.smartek21.com cert (Task #26)
   - `module.auth.aws_cognito_user_pool_client.web` — aliases update
   - `module.data.aws_db_parameter_group.pg16`
   - `module.kms.aws_kms_key.data`, `module.kms.aws_kms_alias.data`
   - `module.observability.*` — CloudTrail, GuardDuty, SNS topic,
     alarms, S3 buckets + policies for CloudTrail
   - `module.schedulers.*` — EventBridge rules, ECS task defs, IAM
     roles, SES identity (~17 resources)
   - `module.secrets.aws_secretsmanager_secret.{db_url, jwt_signing,
     db_password}` — the modules/secrets directory was `.gitignore`d;
     restore it (as a module, not ignored) and adopt the secrets
     that already exist in AWS
   - `module.storage.*` — sows, agreements, audit_exports buckets +
     lifecycle + object-lock configs (~13 resources)
   - `module.api.aws_iam_role_policy.{task_execution_kms, task_kms}`
   - `module.web.aws_s3_bucket_policy`, `aws_s3_bucket_server_side_encryption_configuration`
   Adopt what exists, change nothing. After adoption, `terraform plan`
   on `infra-tf/` must show ONLY the two S14a items:
   `aws_cloudfront_function.spa_rewrite` create + the
   `aws_cloudfront_distribution.web` `custom_error_response` block
   change. Paste that plan in the report as the exit criterion.

3. **Resolve the env layout confusion.** The live env is
   `infra-tf/` root (name_prefix `officeapp-dev`, distribution
   `d1mu2un4hj9akj.cloudfront.net`). `infra-tf/env/staging/`
   (`officeapp-staging-*`) is a fresh root nobody has ever applied.
   Pick one shape:
   - **Option A**: rename `infra-tf/` → `infra-tf/env/staging/`
     (physically or by symlink/README), delete the dead
     `infra-tf/env/staging/` scaffold. Document the rename in
     `docs/adr/`.
   - **Option B**: complete `infra-tf/env/staging/` properly (fix
     the `aws_lb.api` data-source error, add all missing modules,
     apply from scratch on a new name prefix), then plan the rename
     of live from `officeapp-dev-*` to `officeapp-staging-*` — this
     is disruptive; do only if Option A can't work.
   Do NOT keep both. Delete whichever loses.

4. **Fix the `aws_lb.api` data-source error** in
   `infra-tf/modules/web/main.tf:6` — the ALB name lookup should be
   parameterised or resolved via the api module's output, not a
   data source that requires the ALB to already exist.

5. **Prod does not exist yet.** Record this explicitly in the
   report. The tftest `production_cannot_opt_in` in
   `infra-tf/modules/api/tests/dev_seed.tftest.hcl` stands as the
   prod guard until a prod env is added. File
   `docs/backlog/prod-environment.md` so that day is planned
   (account isolation, KMS key, Cognito pool, HubSpot prod app,
   custom domain + ACM cert, prod IAM roles for CD, no dev-seed
   flag) — not improvised. This backlog is not the story to build
   prod; it's the story to think through what prod means so the
   next actual prod slice starts from a plan.

## Definition of done

- `terraform plan` on `infra-tf/` (post-migration, post-adoption)
  shows only the two S14a items. Report includes the full plan
  output.
- `terraform apply` clean (0 side-effect resources) if run today.
- Backend `s3://officeapp-tfstate-.../dealgate/staging/terraform.tfstate`
  exists, lock table `officeapp-tfstate-lock` used.
- Env layout decision recorded in `docs/adr/`; the losing dir
  deleted.
- `docs/backlog/prod-environment.md` committed.
- `docs/reports/s14a.1.md` with: adoption steps, before/after plan
  excerpts, backend migration notes, one line per adopted resource
  with its `terraform import` command (or import block).
- CLAUDE.md rule 12 already in place; s14a.1 is what makes rule 12
  enforceable.

## Not in scope

- **No product code change.** This slice is infra hygiene only.
- **No new AWS resources** except the state bucket + lock table
  (if they don't exist).
- **No prod env**. Only the backlog file that says what prod would
  look like.
