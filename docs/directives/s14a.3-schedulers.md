# Directive S14a.3: schedulers + SES — URGENT (renewal alerts, notifications, audit exports are not running)

From: Kanna Parimi, product owner. 22 September 2026. Commit as
`docs/directives/s14a.3-schedulers.md`. Runs FIRST — before s14a.2
(observability-kms) — and BEFORE s14b's approver-email DoD depends
on the SES identity we're about to create.

## Why this exists (the discovery)

S14a.1's `terraform state` scan proved that `module.schedulers`
never applied. AWS has zero EventBridge rules matching `officeapp`,
zero ECS task definitions in the schedulers family, zero SES email
identities. This means:

- **Renewal alerts don't fire** (Task #24 said "S5 Wave 4 — signed
  SOW distribution + renewals + dashboards" is complete; the
  code shipped but the cron never ran in AWS).
- **Notification queue-drain doesn't run** (S2 Wave 1 stories 12
  et seq. wrote the notification service; the sender is never
  invoked on schedule).
- **Audit exports don't run nightly** (S7 audit-hardening story
  #31 marked complete; the S3 audit bucket doesn't exist and the
  exporter is never invoked).

These are the "S14a-adjacent silent failures" that s14a.1 flushed
out. The task tracker overstates reality — the code paths exist and
have tests, but the deployed system is running without them.

## Correct the task tracker (part of this slice's DoD)

Amend Task #22 (S2/S3 Wave 2 alert scheduler), Task #24 (S5 Wave 4
renewals), Task #31 (S7 Wave 1 audit hardening + observability) to
reflect: **code shipped, deployment incomplete — schedulers module
never applied.** Not their fault at the time; s14a.1's state scan
was the first time the truth surfaced. Note as "reopened by s14a.1;
closed by s14a.3."

## Scope

1. **Apply `module.schedulers` in full** (17 resources per the
   s14a.1 quarantine report):
   - 4 EventBridge rules (alert_scheduler, audit_export,
     notification_sender, renewals_scheduler)
   - 4 event targets
   - 4 ECS task definitions
   - 6 IAM roles + policies (events, task, audit_export_s3,
     events_runtask, events_runtask_audit_export, ses_send)
   - 1 CloudWatch log group
   - 1 SES email identity (this is the s14b prerequisite)

2. **Verify the alert scheduler actually fires end-to-end** — this
   is the DoD proof s14b's approver-email flow will piggy-back on:
   - Seed a fixture SOW whose `notice_date` is 61 days from now.
   - Fast-forward-invoke the alert_scheduler ECS task (via
     `aws events put-events` or a one-off `run-task` with the
     scheduler's task-def, NOT by editing the cron schedule —
     rule 12).
   - Confirm the notification lands in `notification` table with
     status `queued`, then `sent` after the notification_sender
     task-def runs.
   - Confirm the sender attempts SES delivery to a bounce-safe
     mailbox (recommend `staging-inbox@smartek21.com` or a
     dedicated test address; SES identity must be verified).
   - Screenshots + audit-event chain in `docs/reports/s14a.3.md`.

3. **Verify notification queue-drain** — with the same fixture,
   confirm the notification_sender task-def drains within the
   scheduled cadence (default likely 5 min; whatever the module
   sets). Log timestamps.

4. **Verify audit export** — trigger the audit_export task-def
   once. Confirm it writes a JSONL file to
   `s3://officeapp-dev-audit-exports-<accountid>/YYYY/MM/DD/`.
   That bucket must be created (part of the s14a.1 quarantine
   Group Q4 for `audit_exports` — brings that half of Q4 in
   scope with this slice, since audit_export writes there).

5. **Coordination with s14b**: the s14b approvals PR needs the
   SES identity + notification_sender task-def to send approver
   emails. This directive ships those; s14b's proof can then
   rely on them. Do NOT bundle s14b's product code — this slice
   is infra only.
