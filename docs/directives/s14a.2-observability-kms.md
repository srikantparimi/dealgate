## Scope

1. **Apply `module.kms`** — customer-managed KMS key
   `officeapp-staging-data` + alias `alias/officeapp-staging-data`.
   Key rotation ON (annual). Deletion window 30 days. Policy per
   the existing module code (root admin + ViaService delegation +
   CloudFront service principal).

2. **Rotate RDS + Secrets Manager + the web S3 bucket + the
   agreements/audit-exports buckets** to encrypt with the new key.
   - RDS: `aws_db_instance` `kms_key_id` change requires a
     snapshot + restore (RDS can't re-encrypt in place). Plan a
     staging downtime window; the current fixtures are
     regeneratable. Prod version of this rotation is out of scope
     — that will be its own slice with a real snapshot-restore
     plan.
   - Secrets Manager: `aws_secretsmanager_secret.*` `kms_key_id`
     change is in-place; existing versions stay encrypted with
     the old key (Secrets Manager keeps historical versions
     accessible). New versions get the new key.
   - S3 buckets: `aws_s3_bucket_server_side_encryption_configuration`
     `sse_algorithm` from `AES256` to `aws:kms` +
     `kms_master_key_id` set. Existing objects keep their AES256
     encryption (S3 doesn't re-encrypt on config change); a
     background copy-in-place would re-encrypt, but is a separate
     hygiene step, not required for the KMS adoption itself.

3. **Apply `module.observability`** (10 resources):
   - CloudTrail `officeapp-staging-audit` writing to a new
     `officeapp-staging-audit-<accountid>` bucket with
     object-lock + versioning + KMS encryption.
   - GuardDuty detector.
   - SNS topic `officeapp-staging-alerts` + email subscription to
     an on-call address (Kanna to provide; do not hard-code
     personal emails).
   - 3 CloudWatch metric alarms (api_task_failures, rds_cpu,
     rds_free_storage) with SNS as the alarm action.

4. **Apply `module.api.aws_iam_role_policy.{task_execution_kms,
   task_kms}`** — attach the KMS grants to the ECS roles so the
   API can read/write with the new key.

## Verification

- `aws kms describe-key --key-id alias/officeapp-staging-data`
  returns a key with rotation ON.
- `aws cloudtrail describe-trails` shows the new trail
  Multi-region=true, KMS-encrypted, S3 destination set.
- `aws guardduty list-detectors` returns one.
- `aws sns list-topics` shows the alerts topic.
- `aws rds describe-db-instances` shows the KMS key id changed
  (post snapshot-restore).
- Trigger a CloudWatch alarm test (e.g. put a stub metric value
  above threshold) and confirm the SNS email lands. Screenshot.
- The 3 secrets in Secrets Manager show the new `KmsKeyId` on
  their next version (write a dummy version, verify, then
  overwrite back to the prod value).

## Terraform state discipline

- Every apply plan committed to `docs/reports/s14a.2.md`.
- No console clicks; no CLI create-bucket / create-key /
  create-trail. Every AWS-side change lands via terraform apply.
- The RDS snapshot-restore for KMS re-encryption is the one
  operation that involves a manual gate (snapshot ID must be
  handed to Terraform via `snapshot_identifier` on the DB
  instance replacement). Document the two-step: apply
  (creates new DB from snapshot with new KMS key), then delete
  old DB via a targeted destroy or `terraform state rm` +
  `aws rds delete-db-instance` — the latter allowed here because
  destroy of a *replaced* resource is TF-managed, not a bypass.
