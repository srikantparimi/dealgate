# Directive S14a.1b: sows bucket migration + drift adoption + S14a apply + close

From: Kanna Parimi, product owner. 22 September 2026. Commit as
`docs/directives/s14a.1b-sows-migration-and-apply.md`. Runs on the
existing `feat/s14a-cloudfront-api-errors` branch (rebased onto
main post-s14a.1). Closes the S14a lineage.

## Why this exists

S14a.1 landed the S3 backend + secrets-module restoration cleanly.
Its next batch (import the sows bucket) revealed a data-destroying
diff: `object_lock_enabled false→true forces replacement`. Kanna's
decision was **B**: create a new object-lock-enabled bucket,
migrate the ~40 fixture objects, retire the old bucket. Do it NOW
while there is no production data.

Then finish enough drift adoption in `infra-tf/` that a
`-target=module.web.aws_cloudfront_function.spa_rewrite -target=module.web.aws_cloudfront_distribution.web`
plan shows exactly two items (the S14a apply), while the 48 s14a.2 /
s14a.3 creates + the remaining update-in-place items stay in a
plan-visible but deferred-by-directive state.

## Scope

### 1. Sows bucket migration (Terraform-driven, rule 12 clean)

- Update `infra-tf/modules/storage/main.tf`:
  - Rename the current `aws_s3_bucket.sows` resource block to a new
    logical name `aws_s3_bucket.sows_legacy`, and pin its
    `bucket = "officeapp-dev-sows-669810405473"` +
    `object_lock_enabled = false` to match reality. This lets
    `terraform import` adopt the bucket cleanly (zero-diff).
  - Add a NEW `aws_s3_bucket.sows` resource with the intended
    name suffix `-v2` (or `-obj` / whatever the module's naming
    helper produces after `object_lock_enabled = true`), plus its
    5 required child resources (versioning, SSE, PAB, lifecycle,
    object-lock-configuration).
- Terraform ops:
  1. `terraform import module.storage.aws_s3_bucket.sows_legacy officeapp-dev-sows-669810405473`
     + import the 5 legacy configs. `terraform plan -target=...sows_legacy`
     MUST show zero diff. If not, STOP (per Kanna rule 3).
  2. `terraform apply -target=module.storage.aws_s3_bucket.sows`
     (and configs). Creates the new bucket with object lock.
- Object copy (data, not infra — allowed under rule 12):
  3. `aws s3 sync s3://officeapp-dev-sows-669810405473
     s3://<new-bucket> --profile lm-arbiter-poc`.
  4. Verify object count + total size match.
- API cutover (Terraform):
  5. `infra-tf/modules/api/main.tf` — add `SOW_BUCKET` env var to
     the ECS task-def `environment[]` list, referencing
     `module.storage.new_sows_bucket_name`.
  6. `terraform apply -target=module.api.aws_ecs_task_definition.api`
     `-target=module.api.aws_ecs_service.api`. Task-def revision +
     service rollout. Verify `/api/sows/upload` writes to the new
     bucket via one curl.
- Retire the old bucket (Terraform):
  7. Once the API cutover is stable, add a `removed` block for
     `aws_s3_bucket.sows_legacy` in the storage module:
     ```hcl
     removed {
       from = aws_s3_bucket.sows_legacy
       lifecycle { destroy = true }
     }
     ```
     Apply — bucket + its 5 configs get destroyed (S3 requires
     the bucket to be empty first; the sync above emptied the
     source only in an aws s3 mv scenario; for aws s3 sync, run
     `aws s3 rm s3://old --recursive` first, then apply).

## Guardrails

- **Rule 12**: every AWS change is Terraform-driven. S3 data copy
  is DATA and allowed via `aws s3 sync`. Bucket destroy goes via
  the `removed` block, not `aws s3 rb`.
- **Rule 3**: any post-import diff → STOP + investigate. Never
  apply drift away silently.
- **Sequencing**: s14a.3 is URGENT and runs in parallel — do NOT
  touch schedulers / observability modules in this slice.
- **No product code**: this whole slice is TF + one env var change
  in the API task-def config (which is TF, not product code).
